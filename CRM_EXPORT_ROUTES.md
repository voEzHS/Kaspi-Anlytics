# Маршруты выгрузки из CRM — точный путь

*Разведано 12.08.2026. Стоимость разведки: 2 запроса, минимальный интервал
39.9 с, нарушений 0. Всё остальное прочитано из DOM без сетевых обращений.*

> **Сначала — `CRM_RATE_LIMIT_RULE.md`.** Guard ставится и проверяется ДО первого
> действия. Маршрут ниже существует именно для того, чтобы не блуждать по
> интерфейсу: каждый лишний клик стоит запроса.

## ГЛАВНЫЙ ПРИЁМ: читать DOM вместо кликов

Меню, списки готовых файлов, значения фильтров и опции селектов **уже есть в
DOM** — их видно через `javascript_tool` без единого сетевого запроса. Кликать
нужно только то, что реально запускает генерацию или скачивание.

Разведка всей структуры двух страниц обошлась в 2 запроса (две навигации).
Слепое хождение по интерфейсу стоило бы 20-30.

# 1 · ОСТАТКИ

**Страница:** `https://torgstore.zymyran.com/service/warehouse/products/list`

**Кнопка «Опции»** (в шапке таблицы) содержит три пункта:
* `Экспортировать` — id `yuDataAjaxExportExcel`, обычный экспорт видимой таблицы
* **`Экспорт товаров с надстройками`** ← нужен именно этот
* `Прайс-лист`

**Кнопка «Загрузки»** — список УЖЕ СГЕНЕРИРОВАННЫХ файлов с прямыми ссылками:

```
https://cdn.zymyran.com/storage/temp/2026-08-05 15:38:25.xlsx
https://cdn.zymyran.com/storage/temp/2026-08-04 21:46:04.xlsx
```

Имя файла = дата и время генерации, то есть **свежесть снимка видна из имени**.

### Оптимальный порядок (1 запрос вместо 4)

```js
// 0 запросов: прочитать список готовых файлов из DOM
[...document.querySelectorAll('a[href*="storage/temp"]')].map(a=>a.href)
```

1. Прочитать список из DOM → взять самый свежий файл.
2. Если он свежее 7 дней — **просто скачать его, генерацию не запускать.**
   Итого 1 запрос.
3. Если устарел — «Опции» → «Экспорт товаров с надстройками» (1 запрос),
   подождать, перечитать DOM (0), скачать (1). Итого 3.

Ссылки ведут на `cdn.zymyran.com` — это поддомен `zymyran.com`, значит guard их
тоже перехватывает и правило 3 секунд действует. Так и должно быть.

# 2 · ПРОДАЖИ ПО КАНАЛАМ

**Страница:** `https://torgstore.zymyran.com/service/analytics/products/sales`
(навигация: Аналитика → Товары)

**Кнопки экспорта:** `Excel` и `Excel (кастом)` (id `yuCustomExportBtn`).

## ⚠️ ПОЧЕМУ ФАЙЛ ПОЛУЧАЛСЯ УЗКИМ — разгадано (уточнено 12.08)

**Причина одна: ПЕРИОД.** Проверено чтением фактических значений формы —
`moving_city_id`, `city_id`, `warehouse`, `category_id`, `brand_id` и
`sale_channel` уже стояли на «Все»/«Любой». Единственное, что резало данные:

| Поле | Было | Нужно |
|---|---|---|
| `date` | `08/01/2026 - 08/12/2026` — **12 дней** | `07/01/2025 - <сегодня>` — ~13 месяцев |

Формат — **`MM/DD/YYYY - MM/DD/YYYY`** (американский, не европейский). Легко
ошибиться и получить пустой период. Дата **обязательна**: без неё страница
показывает заглушку «Укажите дату или период» и данных не отдаёт.

Поле — daterangepicker. Ставить через API, а не записью в `value`
(иначе внутреннее состояние пикера не обновится и уйдёт старый период):

```js
const drp = jQuery('[name="date"]').data('daterangepicker');
drp.setStartDate('07/01/2025');
drp.setEndDate('08/12/2026');   // 0 сетевых запросов
```

Первоначальная версия этого файла называла второй причиной «один город» —
это было неверно, исправлено после проверки фактических значений формы.

Это снимает разом два пробела, на которые опирается вся модель закупа:
сезонность (нужна история ≥12 мес) и разрез по городам.

## Значения фильтров

`data_type`: `sales` Продажи · `arrival` Приходы · `moving` Перемещения

`moving_city_id`: `0` Все · Алматы · Астана · Шымкент · Актобе · Караганда ·
Тараз · Павлодар · Усть-Каменогорск · Семей · Атырау · Костанай · Кызылорда ·
Уральск — **14 городов**, а не 3. Наши Kaspi-склады только в трёх, но продажи
идут шире.

`sale_channel`: `0` Любой · `2` Розничные продажи · **`3` Каспи** ·
`4` Дилеры · `5` Корпоративные продажи · `7` Айдын Опт · `12` Мастер продаж ·
`14` Customer service · `16` Дефекты · `40` Маркетинг · `41` ИТ отдел ·
**`43` Каспи - Магазин**

> **Находка:** каналов Kaspi ДВА — `3` «Каспи» и `43` «Каспи - Магазин». Для
> расчёта доли Kaspi в расходе общего склада (раздел 9-тер закона) надо
> суммировать оба, иначе доля занижается. Раньше это нигде не учитывалось.

Прочие доступные фильтры: `warehouse`, `warehouse_from`, `warehouse_to`,
`arrival_city_id`, `city_id`, `brand_id`, `category_id`, `status[]`,
`status_moving[]`, `manager_id`, `client_id[]`, `payments_method`,
`payments_bill`, `service_point`, `shipment_point[]`, `promotion`, `sortby`.

### Сохранённый пресет — ПОПЫТКА НЕУДАЧНАЯ (12.08)

Механика кнопки «Сохранить фильтр» (`.yuSaveFiltersBtn`) разобрана:
клик открывает поле `.yuAddSavedFilterInput` (placeholder «Название фильтра»)
и кнопки `.yuAddSaveFiltersBtn` «Сохранить» / `.yuCancelSaveFiltersBtn`.
После ввода имени и клика «Сохранить» чип появляется в `.yuSavedFiltersTabs`.

**Но после перезагрузки страницы пресет исчез** — контейнер `.yuSavedFiltersTabs`
пуст, имени нет нигде в DOM. То есть чип добавился только на клиенте, на сервер
не сохранился.

**Вероятная причина (не проверена):** фильтр сохраняется вместе с ПРИМЕНЁННЫМ
состоянием, а поиск в тот момент не запускался — страница висела на заглушке
«Укажите дату». То есть нужно: выставить фильтры → **выполнить поиск** →
и только потом «Сохранить фильтр».

**Проверять это НЕ приоритетно.** Пресет экономит 1-2 запроса, а маршрут с
точными полями и значениями ниже работает и без него. Гоняться за удобством,
тратя запросы к CRM, — нарушение иерархии приоритетов из `CRM_RATE_LIMIT_RULE.md`.
Если однажды поиск и так будет запущен — попробовать сохранить сразу после
него, это бесплатно.

### Порядок для полной выгрузки

1. `data_type` = Продажи
2. `moving_city_id` = Все (`0`)
3. `sale_channel` = Любой (`0`) — нужны все каналы, склад общий
4. `date` = ~13 месяцев назад — сегодня, формат `MM/DD/YYYY - MM/DD/YYYY`
5. Применить фильтр — **1 запрос**
6. `Excel` — **1 запрос**

Итого 2 запроса при заранее известных значениях. Между шагами 5 и 6 пауза
обязательна.
